# v151 監査ノート ― 読み込み速度の実測と削減

## 実測方法
ローカル配信（ThreadingHTTPServer）＋ Playwright（iPhone 390×844, DPR2, モバイルUA）。
回線スロットリング2条件（4G相当＝下り4Mbps/上り2Mbps/50ms、低速4G相当＝下り1.6Mbps/上り750Kbps/150ms）＋無制限、
キャッシュ無効（cold）／有効（warm）で、ネットワーク転送量とマイルストーン（ロック表示→タップ→ホーム表示）を計測。
※ローカル配信は gzip なし・HTTP/1.1 のため、index.html の転送量は実ホスト（GitHub Pages は gzip 配信、実測 150KB）より大きく出る。バイト量の比較は同一条件の前後比較として有効。

## 実施した削減
1. **BGM の src 遅延**: syncMusic は初回ジェスチャ前（musicStarted=false）に src をセットしないよう変更し、startMusic 側で保留中のトラック src をセットしてから再生開始する分岐を追加。358KB がタイトル画面表示と競合しなくなった（音楽の開始・切替・フェード挙動は従来どおり。実駆動で「タップ前 src なし／タップ後 whisper 再生中／playTrack 切替」を確認）。
2. **プロフィール背景の lazy 化**: #prof-bg に loading="lazy" を付与。updProfile が初期化時に src をセットしても、非表示中は取得されず、プロフィールを開いた時に初めて読み込まれる（クリア済み旧セーブで実測：complete・naturalWidth=1080）。
3. **ホーム写真ウィジェットの lazy 化**: 解放直後の即時スクリーンショットでも表示済みで、ポップインなし。
4. **画像再圧縮**: 全57枚を棚卸しし、削減効果5%以上の21枚だけを q82・プログレッシブ・幅上限1080px で再エンコード（残り36枚は原バイトのまま復元し無駄な churn を回避）。全ファイル PSNR 34.6dB 以上（最小は nao-post1-main）。対象21枚: 4,969KB → 2,182KB（−2,787KB）。ロック画面・IGフィード・プロフィールの前後スクリーンショットで目視差分なし。
   - 主なもの: nao-post1-main 472→201KB / ig-jaeon2-main 463→201KB / ig-army-main 486→230KB / title-keyvisual 200→81KB / ig-butterfly-main 244→103KB
5. **favicon 分離**: 250KB の投稿写真をそのまま参照していた favicon を、同一絵柄の 96×96 専用ファイル assets/favicon.jpg（3.7KB）に分離。

## 削減後の実測（同一条件）
- 初回ロード（タイトル画面が操作可能になるまで）: **1,479KB → 665KB（−55%）**（4G／低速4G条件。残りは index.html 494KB＋KV 81KB＋アバター 88KB＋効果音 1.4KB）
- 低速4G cold のホーム到達: 6.79s → 4.2s（共有VM上の壁時計参考値）
- IG初回表示: 1,468KB → 1,157KB（−311KB）
- warm（キャッシュ有効）: 転送 0KB は従来どおり維持

## 見送った候補
- **index.html の minify**: 実ホストでは gzip で約150KBまで落ちること、手作業で保守する単一ファイルに対して変換リスクと可読性低下が見合わないため見送り。
- **BGM m4a（各約370KB）の再エンコード**: 初回ロードから外れたため優先度が下がったことと、音楽そのものの音質に触る変更になるため見送り。
- **nao-busan-me.jpg / nao-slope.jpg 等の再圧縮**: 元のエンコードが既に効率的で、q82 再エンコードでも 5% 未満の削減（むしろ増えるものも）だったため原バイト維持。
